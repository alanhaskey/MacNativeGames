# 收集同步（克洛格/宝箱/洞穴/魔犹伊/支线）调研

> 结论先行：**可实现，建议第一期用"存档读取"做批量/回填，第二期用"内存读取"做即时事件。**
> 当前只完成调研工具，未改游戏运行时。提交见 `totk-to-wiki` 分支。

## 1. 问题拆解

"地图自动标记完成"需要三件事同时成立：

1. **数据源**：能读到"这个对象已完成"的状态；
2. **身份匹配**：知道读到的状态对应 wiki 地图上的哪个标记；
3. **时效**：玩家完成动作后多久能反映到 wiki（存档时刻 / 实时）。

## 2. 已核实的游戏数据

### 2.1 存档（progress.sav）

`slot_00/progress.sav`（1.4.3，2,307,856 字节）顶部是一张 **30,722 条的哈希表**：
8 字节一组 `u32 key → u32 value`，到结束标记 `0xA3DB7114` 为止。value 里同时存在
`0 / 0xFFFFFFFF`（布尔/计数）和 `0x0001xxxx`（指向数据区的偏移）与浮点位模式（坐标等）。

同一玩家的两个槽位（不同存档时刻）差异只有 **11 个 key**：

```
changed: 0x1EA93BD8 0x4021ABC0 → 0xC041F8CB   (浮点位模式，疑似坐标/朝向)
         0x2BF951D3 0x00000001 → 0x00000000
         0x31AB5580 0x00000003 → 0x00000008
         0x3F8D9D86 0x000013F8 → 0x000013D1   (计数类)
         ...
```

这说明：**一次具体行为只会改动极少数 key**，非常适合做"差异对照"实验。

- 存档里没有可读字符串（名字全部哈希化）。
- 已验证 CRC32 / MurmurHash3-32（种子 0）**不是**存档 key 的哈希函数（对 GameDataList 里的明文名不匹配）；
  需要靠差异实验反推，不能靠猜。

### 2.2 RomFS 里的旗帜清单

`GameData/GameDataList.Product.140.byml.zs`（压缩 2,058,241 → 解压 9,287,060 字节）是游戏的
**全局游戏数据（GameData）定义表**，里面有明文旗帜名，例如：

`OpenTreasure`、`GetTreasure`、`GetThreeTreasure`、`TreasureBox`、`GoToCave`、`TalkOldKorok`、
`Challenge`、`Quest`、`BringCaveMasterMedal`、`WarpToCaveOfAwake`……

- 这些是**任务/挑战/洞穴发现/计数类**旗帜，适合"支线挑战完成""洞穴发现"这类同步。
- 文件用游戏自带的 zstd 字典压缩。仓库里已有现成解法（`scripts/make_button_icons.py`）：
  `Pack/ZsDic.pack.zs` 解出 3 个字典（`zs.zsdic`、`bcett.byml.zsdic`、`pack.zsdic`），
  GameDataList 使用 `dict_id=1`。本次调研已成功解压并确认内容。
- 但它是**全局旗帜表，不是逐对象表**：没有针对每个克洛格/宝箱的独立名字。

### 2.3 RomFS 里的逐对象数据

`Banc/`（137,685 个文件）与 `Cave/`（3,939 个）是分区域的地图/演员数据
（`Banc/MainField/.../Map_*.bcett.byml.zs` 等），是**对象 ID、坐标、类型**的候选来源；
`Banc/MainField/StaticGameDataArea/...` 还与静态游戏数据区域相关。需要进一步解析（bcett 也是 BYML 变体）。

### 2.4 wiki 侧已有的匹配资本

wiki 的标记数据（objmap 导入）已经带有：`sourceId`（objmap 对象 ID）、`objectName`（游戏 actor 名）、
`mapType`/`mapName`/`fieldArea`、精确的 `game{x,y,z}` 坐标。这意味着——
**只要能确定"存档 key ↔ 游戏对象 ID/坐标"的关系，wiki 标记就能直接对上。**

## 3. 两条路线对比

| | 存档读取 | 内存读取 |
|---|---|---|
| 数据完整性 | 权威、可回填历史 | 只有当前会话 |
| 时效 | **只在存档时更新**（神庙/传送/退出等自动存档点） | **即时**（开箱/摘克洛格瞬间） |
| 实现难度 | 中：表结构已解析；难点是 key→名称/对象映射 | 高：需定位运行时 GameData / 场景对象状态结构与指针 |
| 版本稳定性 | 高：表格式简单，1.4.3 已验证 | 低：每次版本更新都要重新定位偏移 |
| 风险 | 低（只读文件） | 中（只读内存，但偏移错会读到垃圾） |
| 适合 | 批量同步、离线补齐、第一期 | 即时反馈、第二期增强 |

**建议：先做存档（P1），再用内存事件补充即时性（P2）。**

## 4. 待解决的关键问题

1. **存档 key 的哈希函数/命名规则**：是 CRC32(对象名+坐标)？还是对象 ID？当前未知。
   → 用"差异对照实验"反推（见 §5）。
2. **逐对象状态的存放位置**：克洛格/宝箱/魔犹伊的完成状态是否在同一张 30,722 条表里，
   还是在另一个 section（例如按区域序列化的 actor 状态）里。→ 差异实验会告诉我们。
3. **对象 ID ↔ wiki 标记**：objmap 的 `sourceId`/`objectName` 与存档 key 的关系。
4. **存档时机**：如果只读存档，玩家完成一个宝箱后要等到下一次自动存档才会同步；
   需要在 wiki 侧显示"上次同步时间"，或者 P2 用内存事件即时标记。

## 5. 下一步实验（高信息量、低成本）

已新增两个只读工具：

- `games/totk/scripts/diag/save_table_diff.py`：dump / diff 存档哈希表；
- `games/totk/scripts/diag/collection_probe.py`：**一键快照 + 对比**（推荐用这个）：

```sh
python3 games/totk/scripts/diag/collection_probe.py snapshot --label baseline   # 动作前
# 游戏里只做一个动作，然后手动存档
python3 games/totk/scripts/diag/collection_probe.py after --label after        # 自动快照并对比上一次
python3 games/totk/scripts/diag/collection_probe.py list
```

快照保存在 `~/Library/Application Support/MacNativeGames/TOTK/collection-probes/`，
同时记录存档时间、槽位、sha256 和当时的玩家坐标（游戏在跑时从 `maplink.json` 读取）。
`diff` 会把每个变化的 key 解成 `int` / `float32` / `flag` 三种视图，方便认出坐标或计数。

**对照实验步骤**（建议在存档副本上做，或先备份整个 profile）：

1. 进游戏，手动存档一次 → 复制 `progress.sav` 为 **A**；
2. 只做一个明确动作：打开**一个**宝箱 / 摘**一个**克洛格 / 拿**一个**魔犹伊 / 完成**一个**支线挑战
   （记下对象在地图上的坐标或名字）；
3. 再手动存档 → 复制为 **B**；
4. 运行 diff，得到变化的 key（预期 1–5 个）；
5. 换一个同类对象重复一次，比较两次的 key 差异 → 可判断 key = f(对象 ID/坐标) 还是 f(类型)；
6. 结合 RomFS 的对象数据与 wiki 标记的 `sourceId/objectName/坐标`，确认匹配方式。

这一步做完，就能确定"存档同步"能否覆盖你要的五类收集，以及需要补多少映射工作。

### 5.1 第一次对照实验结果（2026-10-21，天空岛克洛格，坐标约 246/-822）

- **动作前**：`slot_03` 20:35:03，种子计数 17；
- **动作后**：`slot_00` 20:35:45，种子计数 18（`slot_04` 20:37:20 自动存档同值）。
- `progress.sav` 顶层表只变了 **7 个 key**，其中**没有**新增/置 1 的逐对象 flag：

| key | 变化 | 解释 |
|---|---|---|
| `0x449B3BA6` | 17 → 18 | **克洛格种子计数 +1**（与更早存档 16→17 一致） |
| `0x1EA93BD8` | float | 位置/朝向 |
| `0x46920F1B` | float | 位置/朝向 |
| `0x878AEE40` | float | 位置/朝向 |
| `0x3F8D9D86` | 6006 → 6043 | 时间/帧计数 |
| `0xE573F564` | 7608 → 7645 | 时间/帧计数 |
| `0x2106FA19` | 52 → 30 | 会话/菜单计数 |

- 字节级差异：`progress.sav` 114 字节、`footprint.sav` 23 字节、`caption.sav` 9.6 KB、
  `direct_file_save_related.sav` 0 字节。`footprint.sav` 的 0x150C 起出现一段新增数据，
  疑似"足迹/已解对象记录"，但**尚未解析**；`caption.sav` 的大变化更像地图标签/雾。
- **结论**：存档能可靠给出"收集**数量**"，但这次动作里没有出现"**哪一个**克洛格"的顶层 flag。
  要实现地图上的精确标记，需要走"事件 + 坐标就近匹配"，或先解析 `footprint.sav`。

### 5.2 第二次对照：神庙"发现但未完成"（2026-10-21 20:40 自动存档）

`slot_04`（20:37:20，种子 18）→ `slot_05`（20:40:32）：

| key | 变化 | 解释 |
|---|---|---|
| `0x5F6180D7` | **0 → 1** | **神庙发现 flag**（本次唯一新增的逐对象 flag） |
| `0x449B3BA6` | 18 → 19 | 路上又拾取了一颗克洛格种子 |
| 三个 float / 两个时间计数 | 变化 | 位置、朝向、时间 |

**哈希映射尝试**：把 GameDataList 里的明文名（3373 个候选）与 wiki 侧的 `source_id`
（666 个 `Dungeon:0x<64位ID>`）分别尝试 CRC32 / CRC32C / Murmur3-32 / FNV-1a，并加上常见前缀后缀、
大小端、高低 32 位等组合，**均未命中** `0x5F6180D7`。说明 flag key 的命名/哈希规则不是这些常规组合，
需要更多同类样本或内存侧直接观察。

**结论**：逐对象 flag 确实存在（神庙发现就是一条），只是克洛格那次没有出现。
这提示不同类别用不同的存储方式（或克洛格状态在 `footprint.sav` 的位图里）。玩家位置从存档解出为
`(263.8, 1565.4, 915.7)`，可用来对准地图上的神庙标记。

### 5.3 第三次对照：神庙激活传送点（20:40:32 → 20:46:28）

| key | 变化 | 解释 |
|---|---|---|
| `0x161D8560` | **0 → 1** | 神庙激活/完成 flag 之一 |
| `0xDFA99B55` | **0 → 1** | 神庙激活/完成 flag 之二 |
| `0x5F6180D7` | 保持 1 | 发现 flag（不变） |
| `0x449B3BA6` | **不变** | 激活不增加这个计数 |
| 位置/时间计数 | 变化 | 正常 |

**修正**：用户确认 20:37→20:40 期间**没有**再捡克洛格，只发现了神庙；因此 `0x449B3BA6`
并不是"克洛格种子数"，它更可能是**"地图图标/地点发现"类计数**（克洛格完成、神庙发现都会 +1，
神庙激活不 +1）。具体语义待定，但作为"有事情发生"的触发器仍然有用。

**神庙的完整记录**：发现 = 1 个 flag；激活 = 再 2 个 flag。说明逐对象状态是**一组 flag**，
不是单个 key。

### 5.4 由此得到的 MVP 架构（不需要解开哈希）

把 flag key 当作**不透明 ID**，用"首次出现 + 玩家坐标"建立映射：

1. 每次存档后对比上一份：找出**新出现/置 1 的 key** 与**计数变化**；
2. 若是新 key：取存档里的玩家坐标，绑定到**最近的未完成标记**（类型按 key 的类别/位置推断）；
   绑定关系由 wiki 侧持久化（`key -> markerId`）；
3. 若是已知 key：直接把对应标记标完成；
4. 若是计数变化（无 key，如克洛格）：取玩家坐标，绑定最近的未完成同类标记；
5. 同一存档里出现多个变化时，按"类型 + 距离"排序，把变化分配给最近的候选；
   下一次存档若出现新 key，可用于校正。

这个方案**不需要知道哈希函数**，也不需要逐对象 ID；代价是首次完成时依赖"玩家站在对象旁边"
（对克洛格/宝箱/神庙都成立），且一次存档里发生多个动作时需要消歧。

### 5.5 第四次对照：获得究极手（20:46 → 20:49）与开奖励宝箱（20:51:52 → 20:52:07）

**究极手**：新增 7 个 flag（`0x19C7D1B4`、`0x4884D3FF`、`0x5E6E5C29`、`0x8816DC32`、`0xD3ED7034`、
`0xE019F1A2`、`0xF1DD8751`），并且 `0x449B3BA6` 计数 +1（19→20）；另外两个哈希样字段变化。

**开一个奖励宝箱（获得琥珀）**：新增 **3 个 flag**（`0x1BED068D`、`0x1F23D973`、`0xAD3CBF08`），
`0x449B3BA6` **不变**；位置/时间变化。

**解读**：
- 逐对象状态确实是"一组 flag"，不是单个 key；宝箱 3 个、神庙发现 1 个 + 激活 2 个、能力 7 个。
- 这 3 个宝箱 flag 里，至少有一个应该是"这个宝箱已开"的逐对象 key，其余可能是区域/类别/物品类
  的通用 flag。**需要第二个宝箱**来区分"每次不同的 key"和"每次都一样的 key"。
- `0x449B3BA6` 在克洛格完成、神庙发现、究极手时 +1，宝箱不 +1——更像"重要发现/关键物品"类计数，
  不是克洛格专用；具体语义待定。

## 6. 下一步实验（判断逐对象状态到底在哪）

| 实验 | 动作 | 要回答的问题 |
|---|---|---|
| E2 | **只走路、不收集** 1–2 分钟，前后各存一次 | `footprint.sav` 是否随移动增长（→ 是地图足迹，不是对象） |
| E3 | 在**另一个位置**再完成一个克洛格，前后各存一次 | 是否出现与 E1 不同的变化字节（→ 逐对象记录存在） |
| E4 | 开关一个**宝箱**，前后各存一次 | ✅ 已完成：3 个新 flag |
| E4b | **第二个宝箱**（不同位置），前后各存一次 | 哪些 key 每次都不同（逐对象）vs 每次相同（通用） |
| E5b | 再发现一个神庙 | 神庙发现 flag 是否每个神庙不同 |
| E5 | **完成**当前这个神庙，前后各存一次 | 对比"发现 flag"与"完成 flag"的差异，得到同一对象的两条记录 |

E4 信息量最大：如果宝箱也只在表里改计数，那几乎可以确定逐对象状态在 `footprint.sav` 之类的压缩结构里。

## 8. 风险

- 存档 key 的哈希/命名规则可能不统一（不同系统不同规则），需要按类逐项确认。
- 逐对象状态可能不在 progress.sav 主表，而在按区域的序列化数据里，解析成本更高。
- 不同游戏版本（1.0.0/1.1.2/1.2.1）存档布局不同；本期只针对 1.4.3。
- 只读存档不影响游戏，但**不要**把解析结果当作可写接口。
