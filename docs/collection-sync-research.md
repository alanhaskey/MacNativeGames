# 收集同步调研（固化版）

> 记录时间：2026-10-21。数据来自本机 1.4.3 存档与实机操作，全部只读。
> 配套机器可读记录：[docs/save-event-observations.json](save-event-observations.json)（事件、flag key、计数、坐标）。
> 快照保存在 `~/Library/Application Support/MacNativeGames/TOTK/collection-probes/`。

## 1. TL;DR

- **第一期用存档读取即可**，不需要内存读取：存档里有"**新置 1 的 flag 组**"和"**存档时的玩家坐标**"。
- **不需要破解哈希、不需要逐对象 ID**：把每次事件产生的 flag key 当作**不透明 ID 组**，用坐标就近绑定到
  wiki 标记，wiki 侧持久化 `key组 → 标记`。第一次之后同组 key 再出现就能识别。
- **克洛格没有逐对象 flag**（本次观测），只有计数变化；用"计数增量 + 坐标"匹配最近标记。
- 内存读取只在需要"**完成瞬间即时标记**"时才需要，第一阶段不做。
- 已知限制：一次存档内发生多个事件时需要用类型/距离消歧；不同类别（宝箱/神庙/能力/克洛格）flag 组大小不同。

## 2. 两条路线（结论：先存档）

| | 存档读取 | 内存读取 |
|---|---|---|
| 数据 | flag 组、计数、存档时坐标 | 事件瞬间的状态 + 实时坐标 |
| 时效 | 只在存档点（自动存档很频繁：神庙、传送、发现等） | 即时 |
| 实现成本 | 低：表结构已验证，解析简单 | 高：需要定位运行时状态结构与指针，版本敏感 |
| 风险 | 低（只读文件） | 中（偏移错误会读到垃圾） |
| 结论 | **第一期采用** | 第二期可选增强 |

## 3. 存档格式（已验证）

`slot_XX/progress.sav`（1.4.3，2,307,856 字节）：

- 头 8 字节：`magic = 0x01020304`，header = `0x49E946`；
- 从 `0x28` 开始是 **30,722 条 `u32 key → u32 value`** 的哈希表，结束标记 `0xA3DB7114`（约 `0x3C038` 处）；
- 玩家坐标通过标签定位：`0xC884818D`（PlayerStatus.SavePos）、`0x8773F02D`（World_PlayerPos），值为 3 个 float32；
- 表里 value 兼有：`0/1`（flag）、计数、float 位模式；flag key 无明文名字。
- 文件其余部分是按标签偏移指向的数据区（坐标、场景/对象数据等）。

同一动作的字节级变化很小（本次宝箱前后：`progress.sav` 约 100 字节、`footprint.sav` 23 字节）。

### 4.0 游戏内时间字段（已确认）

用玩家报告的 HUD 时间对照存档，确认两个字段：

| 字段 | key | 范围 | 验证 |
|---|---|---|---|
| 游戏内小时 | `0x449B3BA6` | 0–23 | 21:18:33 存档 = 8 点；21:19:42 = 8 点 |
| 游戏内分钟 | `0x2106FA19` | 0–59 | 21:18:33 = 0；21:19:42 = 5（8:00→8:05）；22:06:40 = 41（玩家报 23:40） |

顺带发现：这意味着**"世界信息"里的游戏内时间可以直接从存档拿到**（最后一次存档时的时刻），
不需要内存读取；实时时间仍需要内存。

### 4.05 数据区里还有"真实状态"（重要）

21:44 那个宝箱在**表里没有任何 flag**，但整文件字节对比显示数据区有一段被改写：

- `progress.sav` 共 876 字节变化，其中表内只有位置/时间（15 字节）；
- 数据区 `0x0D9560..0x0D9868` 约 **700 字节**变化，`0x0D9510` 起是一串 **8 字节 ID**（在开箱/神庙/克洛格时都会变，开箱时增长）；
- 这些 64 位 ID 与 wiki 标记的 `source_id`（`Dungeon:0x...`）**不相等**（大小端都试过）。

结论修正：**宝箱的真实"已开"状态在数据区 blob 里，而之前看到的 2~4 个 flag 更像"成就/首次物品"类附加 flag**
（所以组大小会变）。这带来两点：

1. 事件检测可以靠"数据区变化 + 坐标"，不需要解出 ID；
2. **回填/枚举已开的宝箱**需要解码这个 blob（8 字节 ID 列表），目前未解出。

### 4.1 关键观察

1. **逐对象身份存在，但是一组 flag**：宝箱、神庙、能力的 flag 组互不重叠；
   一个神庙从发现到完成累计 **13 个不同 key**（1 + 2 + 10）。
   **神庙发现 flag 每个神庙不同**：第一座是 `0x5F6180D7`，第二座是 6 个新 key（与之无交集）→ 逐对象成立。
   **完成 flag 也是每座不同**：第一座 10 个 key，第二座 7 个，两者无交集；第二座同一次增量还包含
   "祝福之力 + 电池一组"可能带来的 flag。
   同一次发现里还伴随若干**计数器**（`0x16D9641D`、`0x63866C56`、`0x9DD69D5F`、`0xC41B7240`），
   以及"神庙激活计数" `0x161D8560`（1→2），要按计数器而非逐对象 flag 处理。
2. **两次宝箱的 key 组没有交集**：`{0x1BED068D,0x1F23D973,0xAD3CBF08}` vs `{0xDBEA8E06,0xF9525C48}`
   → 每组里至少有一个逐对象 key，绑定时整组视为该事件的身份即可。
   （注意：只在"第一次"出现的通用 key 不会在第二次 diff 里出现，所以"无交集"不能证明全是逐对象，
   但按组绑定仍然成立。）
3. **克洛格有逐对象 flag，每只 1 个**：第二只 `0xB33C6725`、第三只 `0xE5203D31`，互不相同。第一次"看不到 flag"是
   窗口归因错误：那次窗口同时包含 6 个 flag，其中除克洛格本身外还有"首次存档/菜单"等一次性 flag
   （它们之后一直是 1）。所以克洛格也可以走 flag 组同步。
4. **`0x449B3BA6` = 游戏内小时、`0x2106FA19` = 游戏内分钟（已确认）**：玩家报告 21:18:33 存档为
   8:00、21:19:42 为 8:05，两个字段分别读出 8/0 与 8/5，完全吻合。它不是事件计数，**不能当事件触发器**。
5. **哈希没有破解**：用 GameDataList 的 3,373 个明文名与 wiki 的 666 个 `source_id`，套
   CRC32 / CRC32C / Murmur3-32 / FNV-1a（含前后缀、大小端、高低 32 位）都无法得到这些 key。
   因此**不要依赖名字映射**。
6. **存档里有坐标**：绑定标记只需要存档里的玩家坐标，不用读内存。

## 4.5 参考项目验证：yalincc/totkmap（2026-10-21，重大更新）

社区项目 [yalincc/totkmap](https://github.com/yalincc/totkmap)（JS，支持 Eden/Ryujin）直接解析 `progress.sav`，
与本仓库的逆向结果互相验证，并补上了关键缺口：

| 结论 | 证据 |
|---|---|
| 存档 hash 表的键 = **murmurhash3 x86_32(名字)** | `hash('Complete') = 0x4C0A63F4`（项目注释中的固定值），本仓库独立实现命中 |
| 哨兵 `0xA3DB7114` 的 value = **GUID 数组偏移** | 本机存档读出 `0xD9510`，正是我们之前当作"blob"的那段 8 字节 ID 列表 |
| 我们的观测 key 全部可归名 | `0x5F6180D7`/`0xDF539D50` → `SHRINES_FOUND`；`0x03B85CAE` → `SHRINES_STATUS`；`0xB33C6725`/`0xE5203D31` → `KOROKS_HIDDEN`；`0xE713E9E7` → `LOCATION_CAVES_VISITED`（CentralHyrule_0017） |
| 类别统计正确 | 用该项目的哈希表读本机存档：神庙 2/152、神庙 Clear 2、克洛格 3/800、洞穴 1/151、井 0 —— 与玩家实际进度一致 |
| **魔犹伊 = GUID** | 击败魔犹伊后存档 GUID 数组 +5 条，其中 `0x1c2a653e0d7517d5` 在 `BUBBULS_GUIDS` 列表中（验证通过） |
| **开宝箱也会 +1 条 GUID** | 残旧外衣宝箱窗口：GUID 129 → 130（宝箱可能可以靠 GUID 枚举，不一定需要内存方案） |
| 任务完成 | 键 = `hash('Step_' + 任务key)`，值 = 当前阶段名哈希，`hash('Complete')` 即完成（项目实测 285/285） |

**新方案（替代原来的"不透明 flag 组 + 坐标绑定"作为主路线）**：

1. 游戏侧只做"**解析后的存档状态**"接口：hash 表（hash→value）+ GUID 数组 + 存档坐标 + 游戏内时间 + 版本；
2. wiki 侧持有/生成哈希类别表（神庙/克洛格/洞穴/井/树根/塔/龙之泪/魔犹伊/遗志/卡邦达/怪物等）与标记映射，
   直接按"对象完成"精确标记，不需要猜 flag 组；
3. 逐点映射：塔/龙之泪/魔犹伊项目已有 `markerId→hash/GUID` 表；神庙/克洛格/洞穴需要从 RomFS 地图对象数据生成；
4. 宝箱：先确认能否从 RomFS 生成"宝箱 GUID → 坐标/标记"映射（GUID 数组已含宝箱）；
5. 内存事件保留为"即时性/兜底"（例如需要开箱瞬间推送时）。

**注意**：该项目无 LICENSE 文件，哈希表来自游戏数据/第三方（`marcrobledo/savegame-editors` MIT 的解析思路）。
我们只把它当**验证参考**；正式实现优先从 RomFS 自行生成映射表，或另行确认授权。

## 5. 存储模型结论

- 游戏把"对象状态"存成 **若干不透明 32 位 flag**（一组），而不是一个可读 ID；
- 同一对象的不同阶段（发现/激活/完成）是**不同 flag**，互不覆盖；
- 不同类别 flag 组大小不同：克洛格 0、宝箱 2~3、神庙发现 1 / 激活 2 / 完成 10、能力 7；
- 物品（琥珀/蛋白石/祝福之光）本身没有出现在计数里，不影响"对象完成"的判定；
- `0x449B3BA6`/`0x2106FA19` 是游戏内时间（小时/分钟），**不要用它们当事件触发器**。

## 6. 推荐方案（第一期）

### 6.0 检测信号（最终版）

每次存档变化检测三类信号，全部只读：

1. `newFlags` / `removedFlags`：表里的 0/1 flag 变化（神庙发现/完成、克洛格、能力等）；
2. `counterDeltas`：表里的计数变化（注意排除小时/分钟与已知时间字段）；
3. `changedRegions`：**数据区**变化的字节区间（offset + length + CRC），附带噪声白名单
   （坐标/朝向块 `0x53300..0x53400`、时间/会话计数、以及已知的相机/声音指针），用于宝箱等"状态在 blob 里"的对象。

### 6.1 游戏侧接口（新增）

game 内置网关新增只读接口，暴露"每次存档的增量"：

```json
GET /v1/progress/changes?since=<seq>
200 {
  "schema": "macnativegames.progress/1",
  "game": "totk", "version": "1.4.3",
  "saves": [
    { "seq": 12, "slot": "04", "savedAt": "2026-10-21T13:01:26Z",
      "position": { "x": 281.7, "y": 1498.3, "z": 924.4 },
      "newFlags": ["0xDBEA8E06", "0xF9525C48"],
      "removedFlags": [],
      "counterDeltas": { "0x449B3BA6": 0 } }
  ]
}
```

- 网关监视 `<profile>/save/*/slot_*/progress.sav` 的 mtime；变化时解析表、与上一版 diff；
- 只返回**增量**（新置 1 / 变成 0 的 flag、计数变化），不返回全表；
- 附带存档内的玩家坐标与时间；`seq` 单调递增，供消费者断点续读；
- 只读、回环、无 Python；能力位 `progress: { changes: true }`。

### 6.2 wiki 侧绑定算法

```
for each change C in /v1/progress/changes:
    if C.newFlags is empty and no counter delta: continue
    P = C.position
    candidates = markers near P that are unfinished and of a known type
    if C.newFlags matches a stored group (exact set or overlap):
        mark that marker complete
    elif group size is unexpected for the inferred type:   # first-time UI flags混入
        queue for review; do not mark blindly
    else:
        marker = nearest candidate (type inferred from group size / context)
        bind(group(C.newFlags), marker)
        mark it complete
    if only counter delta (korok):
        mark the nearest unfinished korok marker to P
```

- 绑定关系存在 wiki 侧（`keyGroup → markerId`），换设备/换会话不丢；
- 一次存档多个变化时按"类型 + 距离"分配；不确定的进**人工确认队列**，不要错误标记；
- 克洛格用"计数增量 > 0"触发，匹配最近未完成克洛格；计数语义未知，只当触发器。

### 6.3 覆盖矩阵

| 类型 | 存档里能拿到 | 方案 |
|---|---|---|
| 神庙发现/激活/完成 | flag 组 | 绑定组 → 神庙标记 |
| 宝箱 | flag 数在 0~11 波动（成就/首次物品类，非逐对象） | **存档只能尽力而为**；可靠同步需内存事件 |
| 能力/关键物品 | flag 组 | 可做成就/进度展示，不必绑定地图 |
| 克洛格 | flag（每个 1 个；首次窗口混入一次性 flag） | 绑定组 + 坐标匹配 |
| 魔犹伊/洞穴/支线 | 未测 | 按同样方法采一次样本即可判断 |

## 9. 风险

- **洞窟发现可靠**：干净 30 秒窗口得到 2 个 flag（`0x0E76344B`、`0xE713E9E7`），与之前混合窗口里的两个一致，
  第三个 `0x2539B0FC` 归因于战斗/宝箱。
- **宝箱很可能不能只靠存档同步**：两次观测都指向"开箱没有身份 flag"——21:44 那次 0 flag；
  21:55 那次窗口混入了 3 只怪和物品，唯一的 flag 不能归因。真正的状态在数据区 blob，而 blob 在走路时也变，
  所以"blob 变化"不是事件信号。宝箱需要第二期内存事件或解码 blob；**还差一次真正干净的开箱测试**。
- **有些对象有前置条件**（例如完成怪物狩猎才出现/可开的奖励宝箱），一次存档增量可能同时包含多个事件
  （挑战完成 + 宝箱打开）。绑定算法要把"混合增量"当作多事件处理：按标记类型/位置拆分，拆不出来就进人工确认。
- **窗口长度限制**：接口要带每次存档的 `savedAt` 与与上一次存档的间隔；间隔很长（>2 分钟）的增量视为
  多事件，优先人工确认。干净样本（克洛格 #2：14 秒窗口）与脏样本（旅行克洛格：7.5 分钟、9 个 flag）
  已经都记录在案。
- flag 组可能包含"首次/通用"key（例如首次手动存档/打开菜单），首次绑定时会一起绑到那个对象；
  之后不会重复，通常无害，但 wiki 侧应保留"组大小异常 → 人工确认"状态。
- 一次存档内多个事件同时发生（例如自动存档时刚好开了宝箱 + 发现地点）会导致组混合，需人工确认；
- 只读存档；不要把解析结果当写接口。
- 不同版本的坐标标签/表结构可能变化，接口要带 `version`。

## 9.5 后续计划（2026-10-21 决策）

- 宝箱**必须同步**，因此内存事件方案提前（不再只等第二期）：
  1. 用存档 blob 里稳定的 8 字节 ID 在游戏内存中扫描，定位"已处理对象列表"在内存里的位置；
  2. 监控该列表增长的时间点 → 即"对象刚完成"的瞬间，取当时玩家坐标；
