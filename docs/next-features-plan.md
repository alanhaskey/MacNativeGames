# 下一步功能规划（游戏侧）

> 状态：规划，未实现。前置：位置域与内置网关已完成（[docs/game-interface.md](game-interface.md)），
> wiki 侧实时定位已实装。本文只覆盖**游戏侧**要做什么、按什么顺序、验收标准与风险；wiki 侧的消费与 UI 不在本仓库。

## 1. 现状

| 能力 | 状态 |
|---|---|
| 位置（10 Hz、inWorld、status） | 已实现，内置网关随游戏启动 |
| 网关（`/v1/meta`、`/v1/state`、`/v1/stream`、`/v1/health`） | 已实现，回环、发现文件、探针 12 项 |
| wiki 侧实时定位 | 已实装（外部） |

## 2. 规划原则

1. **先只读、后写入**：写操作（传送/标记）风险最高，放到最后，并且默认关闭。
2. **能不改游戏就不改**：轨迹、存档摘要都可以在网关里完成，游戏本体不动。
3. **每项独立可交付**：一个功能一个端点/能力位，wiki 侧可按能力位逐个接入。
4. **契约先行**：先定 JSON 与状态语义，再实现；只增不改，能力位协商。
5. **可验证**：每项都要有 fixture 探针；写操作额外要真实游戏内验收。

## 3. 进度（2026-10-21）

**M1 已实现并合并**：F1 轨迹（网关内存 2 Hz / 10 分钟 / gap 标记）与 F2 存档摘要（`/v1/save/slots`、
`/v1/save/summary`：位置、savedAt、槽位），探针 23 项通过；心/耐力/卢比仍为空（F3）。

## 4. 候选功能与优先级

| 编号 | 功能 | 风险 | 游戏侧改动 | 估算 | 建议 |
|---|---|---|---|---|---|
| F1 | **轨迹**（最近 N 分钟路径） | 极低 | 仅网关内存缓冲 | 0.5–1 天 | **已实现** |
| F2 | **存档摘要**（上次存档位置/时间/槽位） | 低 | 仅网关解析存档（只读） | 1–2 天 | **已实现** |
| F3 | 存档摘要增强（心/耐力/卢比/时长） | 中 | 网关解析 + 逆向标签 | 2–3 天 | 视需求 |
| F4 | 世界信息（区域/天气/游戏内时间） | 中 | 需要定位游戏内状态 | 3–5 天 | 后置 |
| F5 | 控制域 MVP：传送 | **高** | 游戏侧命令通道 + 备份/门禁 | 3–5 天 + 评审 | 最后，可选 |
| F6 | 游戏内标记（waypoint） | 高，可行性未知 | 需逆向地图钉系统 | 先调研 | 研究项 |
| F7 | 多版本/BotW | 中 | 各域按版本校验 | 按需 | 按需 |

### 3.1 为什么先做 F1 + F2

- **F1 零游戏改动**：网关已经在内存里收到 10 Hz 位置，加一个环形缓冲就能提供"最近 10 分钟"端点；
  wiki 地图立刻可以画路径，且不产生任何磁盘/隐私负担（默认不落盘）。
- **F2 价值互补**：实时定位解决"现在在哪"，存档摘要解决"上次在哪、什么时候、哪个槽"；游戏没开时地图也有内容。
- 两者都是只读，不需要存档备份、不碰游戏状态，出问题最多是接口返回错误。

## 4. F1 轨迹

### 4.1 契约增量

```
GET /v1/trail?seconds=120&max=600
200 {
  "schema": "macnativegames.trail/1",
  "source": "gateway",
  "seconds": 120,
  "points": [
    {"t": 1792547577109, "x": 0.25, "z": 32.21, "yaw": 3.0, "inWorld": true},
    {"t": 1792547577609, "x": 0.30, "z": 32.40, "yaw": 4.2, "gap": true}
  ],
  "truncated": false
}
```

- 采样 2 Hz（位置 10 Hz 去重），缓冲区最多 10 分钟 / 2400 点。
- `gap:true` 表示与上一点间隔 > 2 s（暂停、菜单、卡顿），消费者画断线。
- 仅在 `inWorld=true` 时记录；菜单/加载不计入轨迹。
- 内存型：游戏退出即清空；**不落盘、不上传**（隐私决策 3 的延伸）。
- 能力位：`capabilities.trail = { available: true, maxSeconds: 600, rateHz: 2 }`。

### 4.2 实现（游戏侧）

- `runtime/gateway.c`：在 `runtime_gateway_publish()` 里把点写入环形缓冲（固定数组，无动态分配）。
- 请求时按时间窗裁剪，拼 JSON（复用现有 `build_state` 的风格）。
- 内存：2400 点 × ~40 字节 ≈ 100 KB。
- 探针：`tests/gateway/probe.c` 增加轨迹用例（窗口裁剪、gap、上限、菜单不记录）。

### 4.3 验收

- 游戏内走一段路：`/v1/trail?seconds=60` 返回点序与地图路径一致，误差不超过一个采样点。
- 菜单/加载期间无新点；切回来出现 `gap`。
- 连续运行 10 分钟以上内存稳定、点数不超过上限。
- 关游戏后端点不存在（随网关关闭）。

## 5. F2 存档摘要

### 5.1 可行性实测（1.4.3）

只读探测了用户的 `slot_00/progress.sav`：

| 项 | 值 |
|---|---|
| 文件大小 | 2,307,856 字节（1.0.0 是 2,307,552；1.1.2/1.2.1 是 2,307,656，**布局不同**） |
| magic / header | `0x01020304` / `0x49E946` |
| 位置标签 | `0x8773F02D`（World_PlayerPos）、`0xC884818D`（PlayerStatus.SavePos）都存在 |
| 解出的坐标 | (451.39, 1551.81, 896.76) / (451.45, 1551.90, 896.66) — 合理（天空区高度） |

结论：**位置可以按标签哈希扫描解析，不依赖文件大小白名单**；1.4.3 的 header 与旧版本不同，但标签仍在。
心/耐力/卢比等字段需要另找标签哈希（社区/逆向），放在 F3。

### 5.2 契约增量

```
GET /v1/save/slots
200 { "schema":"macnativegames.save/1", "slots":[
       {"slot":"00","savedAt":"2026-10-21T11:24:00Z","size":2307856},
       {"slot":"01","savedAt":"2026-10-21T04:52:00Z","size":2307856} ] }

GET /v1/save/summary?slot=latest      # latest = 最近修改的槽
200 { "schema":"macnativegames.save/1", "ok":true, "game":"totk", "version":"1.4.3",
      "slot":"00", "savedAt":"2026-10-21T11:24:00Z",
      "player":{"x":451.39,"y":1551.81,"z":896.76},
      "optional":{"playtimeSeconds":null,"hearts":null,"stamina":null,"rupees":null} }
```

- `savedAt` 取文件 mtime；`ok:false` 表示没有可读存档。
- 只读；**不提供原始存档**。
- 存档正在写入时（mtime 刚变、大小不稳定）返回 409 `bad-state`，让消费者稍后重试。
- 能力位：`capabilities.save = { summary: true, slots: true, fields: ["position","savedAt","slot"] }`。

### 5.3 实现（游戏侧）

- 网关新增 `save.c`：定位 `<profile>/save/<hash>/slot_*/progress.sav`（`TOTK_PROFILE_DIR` 环境变量），
  扫描标签哈希（与 `scripts/diag/save_position.py` 同一思路，纯只读），解出位置。
- 按 (路径, mtime, size) 缓存，避免每次请求都读 2.3 MB。
- 不写任何文件；不修改存档。
- 探针：用一份**合成存档 fixture**（带正确标签与坐标）测试解析、槽位选择、坏文件、写入中状态。

### 5.4 验收

- 游戏内手动存档后，`/v1/save/summary` 的位置与游戏内一致（误差 < 1 m），`savedAt` 正确。
- 游戏未运行时（网关不存在）——由消费者显示"游戏未连接"，与位置域一致。
- 两个槽位都能列出，`latest` 选最近修改的。
- 读取过程中存档被覆盖：返回 409，不返回半截数据。

## 6. F3 存档增强（可选）

- 目标字段：心/耐力上限与当前值、卢比、游戏时长、神庙/完成度（后者可能不在 progress.sav）。
- 需要逆向：标签哈希（可以从社区存档编辑器/研究资料得到**思路**，代码必须自己写）、字段编码（int/float/数组）。
- 风险：不同版本布局不同；字段语义要逐项验证（对照游戏 UI）。
- 建议：先把 F3 的字段列成表，逐项"解得出 + 对得上 UI"再发布；不在契约里承诺时间。

## 7. F5 控制域（传送）——高风险，最后做

### 7.1 可行性

- 传送原语**已验证**：`survey move`（`forceSetMatrix`，按帧写入，含旋转校验）在 1.4.3 上工作，
  且 `world_survey.c` 已有逐版本常量和合理性检查（坐标范围、旋转矩阵）。
- 产品化缺的是**安全边界**，不是技术。

### 7.2 必须先落实的安全设计

1. 默认关闭：`TOTK_CONTROL=1` 才启用；网关控制端点另需 `X-Control-Token`（`<data>/control.token`，0600）。
2. 首次写操作前**强制备份**当前槽的存档（`profile-before-control-<ts>`），失败则拒绝。
3. 只允许 `inWorld=true` 且不在菜单/对话/过场中。
4. 传送后按帧保持（如 30 帧）并核对落地位置；失败返回 `rejected` + 原因。
5. 限速：1 次/秒、每会话 100 次；命令 5 秒过期；同一时刻只执行一条。
6. 记录每条命令与结果到游戏日志；不记录 token。
7. 明确告知用户风险（可能影响任务状态/存档），由 wiki 侧在 UI 里二次确认。

### 7.3 契约增量（摘要）

```
POST /v1/control/teleport { "x":..., "y":..., "z":... }
200 { "id":"c-0001","status":"done","frame":123456 }
403/409/423/504 见 docs/game-interface.md §8
```

命令 ABI：网关写 `<data>/control.txt`，游戏轮询执行，结果写 `<data>/control-results.jsonl`。

### 7.4 验收

- 只有开启开关 + token 正确时端点才可用；默认 501/403。
- 菜单中调用返回 409；连续调用触发限速。
- 每次写操作前有备份目录，且备份可被 `--check` 之外的手动恢复流程验证。
- 传送后位置、地形碰撞、存档保存/读取正常（真实游戏内手测）。

## 8. F4 世界信息 / F6 标记 —— 研究项

- **世界信息**（区域名、天气、游戏内时间）：需要定位游戏内状态结构；区域名也可以先用坐标 + wiki 现有
  数据在地图侧算（不需要游戏侧）。天气/时间需要 RE，价值中等。
- **游戏内标记（waypoint）**：要往游戏地图钉系统里加标记，未知是否有稳定入口；先做**只读调研**
  （能否找到地图钉列表/添加函数），再决定是否进入契约。传送是已证明可用的替代思路，但副作用更大。

## 10. 需要拍板

1. F1 轨迹：内存型（重启清空、不落盘）是否可接受？保留时长 10 分钟够吗？
2. F2 存档摘要：首批只做"位置 + 时间 + 槽位"够用，还是必须一并有心/卢比（会拉长到 F3）？
3. M3 二选一：先做**世界信息（只读、安全）**，还是直接做**传送（高风险、需要评审）**？
4. 是否需要支持 1.0.0 / 1.1.2 / 1.2.1 / BotW（会成倍增加每个域的校验工作）。
5. 存档摘要是否要暴露多个槽位，还是只给 `latest`。

## 11. 不做的事

- 不做登录/连接器/上传/地图 UI（外部实现）。
- 不做原始存档读取、内存读写、任意命令执行。
- 不做长期轨迹入库（隐私决策 3）；轨迹只在网关内存里，退出即失。
